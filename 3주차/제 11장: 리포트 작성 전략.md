## 좋은 리포트란, 마크다운 사용법 등

### HackerOne

Report format

1. Asset
    
    버그사에서 다루고자 하는 대상을 선택하는 부분
    
2. Report Template
    
    보고서 작성을 위해 미리 정의된 템플릿 중에서 선택할 수 있다.
    
    선택한 템플릿은 보고서의 구조와 명식을 제시해주며 효율적인 보고서 작성을 돕는다.
    
3. Weakness
    
    발견한 취약점의 종류를 선택
    
4. Severity (optional)
    
    발견한 취약점의 심각도를 추정 (None, Low, Medium, High, Critical)
    
5. Proof of Concept
    
    보고서의 핵심 부분으로 발견한 취약점을 제한할 수 있는 방법을 명확하게 제시해야한다. 이는 보고서의 검진을 돕고 보안팀이 취약점을 신속하게 확인할 수 있도록 한다.
    

### Google

Report format

1. Report description
    
    버그에 대한 간단한 설명을 작성
    
2. Bug location
    
    취약점을 발견한 제품이나 웹사이트를 선택하고 해당 취약점이 있는 url 또는 저장소를 지정
    
3. The cause
    
    취약점의 유형을 선택
    
4. Does anyone else know about this vulnerability?
    
    다른 사람이 해당 취약점을 이미 알고 있는지 여부를 선택
    
5. The problem
    
    취약점의 기술적 세부사항 설명
    
6. Please briefly explain who can exploit the vulnerability, and what they gain when doing so
    
    해당 취약점을 악용할 수 있는 사람과 그들이 악용했을 때 얻을 수 있는 것에 대해 간단히 설명
    
7. Upload file
    
    취약점에 대한 추가 정보를 제공하기 위해 파일을 청구할 수 있음
    

### Naver

Report format

1. 제목
    
    버그를 간략하게 요약하여 작성
    
2. 소속
    
    선택사항이며 제보자의 소속을 작성할 수 있음
    
3. 환경
    
    웹, 안드로이드, ios, 윈도우 중 어떤 환경에서 취약점을 발견했는지 선택
    
4. 서비스
    
    어떤 네이버의 서비스에서 취약점을 발견했는지 선택
    
5. 도메인
    
    취약점이 발견된 도메인을 지정
    
6. 취약점의 종류
    
    CSRF, XSS, RCE, SQL Injection 등 여러가지 취약점 유형 중에서 해당되는 것을 선택
    
7. 취약점 설명
    
    발견한 취약점에 대한 자세한 설명 작성
    
8. 제보자가 생각하는 조치 방안
    
    선택사항이며 제보자가 생각하는 취약점 해결 방법을 작성
    
9. 첨부 파일
    
    추가 정보를 제공하기 위해 파일을 첨부할 수 있음
    

### 요구하는 공통 요소

- 취약점 한줄 요약
- 취약점 발현 방법
- 취약점의 Impact (CVSS 3.1)
- 취약점의 발생 원인 (기술적)
- 조치 방안

### 버그헌팅에서 자주 범하는 실수

#### 범위 확인 미흡

- 구글은 어플리케이션 인수 후 6개월의 blackout 기간을 관찰
- 대부분의 버그헌팅 프로그램은 0-day나 새로 인수한 프로그램에 대해 신고하기까지 버퍼 타임을 부여
- 항상 버그헌팅 프로그램의 프로그램에서 취약점을 찾고자하는 타겟이 In-scope인지 확인이 필요

#### 범위가 아닌 어플리케이션 버그 제보

- 타겟이 아닌 타겟의 로고를 사용하는 공급업체나 파트너사가 아닌지 확인
- 타겟의 로고가 있는 모든 것이 타겟에 속하는 것이 아님을 주의
- IP주소가 타겟을 가르키는지 whois에서 확인
- 도메인 이름이 타겟에 속하는지 DNS 확인
- 타겟 또는 타겟이 인수한 브랜드가 맞는지 확인

#### 자동화 도구의 맹목적 믿음

- 적절하게 구성된 자동화 도구는 수동으로 찾기 매우 어려웠을 버그를 신속하게 식별하는 데 도움이 될 수 있음
- 하지만 그와 동시에 자동화 도구의 결과는 완벽하지 않음
- 구글은 취약한 TLS/SSL 설정, SQL Injection, CSRF, HTTP 헤더 출력 등 많은 자동화 도구의 리포트를 받았지만, 익스플로잇이 가능한 경우는 드물었음
    - 실제로 구글은 2014년, SQL Injection을 80여건 제보를 받았지만, 그 중 하나도 보상으로 이어지지 않음
    - 취약한 TLS/SSL의 설정 보고서 또한 많이 받았는데, TLS/SSL의 버전은 낮지만 TLS 레코드 분할을 사용해 BEAST완화, TLS 폴백 방지를 사용해 POODLE 등의 SSL 취약성을 완화하고 있었음
- 버그 헌팅을 성공하려면 실제 공격이 가능한 시나리오를 만들고 증명하고 제안해야 함. 즉 신뢰하되, 검증하라

#### 불필요한 영상 제보

- 영상이 꼭 필요한지 생각해보기. 영상을 제보받는 보안 전문가들은 다음의 노력이 필요해짐
    - 영상을 제보받는 보안 전문가들은 영상을 보고 적절한 순간에 일시 중지 URL 및 기타 관련 세부 정보를 기록하는 노력이 요구됨
- 영상을 첨부하는 것이 도움이 된다고 생각하거나, 요청을 받은 경우엔?
    - 영상과 함께 서면 지침이 포함되어 있는지 확인해세부 사항을 수동으로 기록할 필요가 없게 하기
    - 영상을 가능한 짧게 유지하고, 공격을 실행하는데 필요한 모든 단계를 녹화하기
    - 영상에 표시된 텍스트를 읽을 수 있도록 해상도와 비트 전송률이 충분한지 확인하기

### 공격 시나리오 작성

- 공격 시나리오 작성은 본질적으로 다음에 대한 간략한 요약
    - 특정 취약점을 악용하려는 사람
    - 어떤 이익을 위하는지
    - 어떤 방식으로
- 구글이 SAML 구현 프로토콜에 대한 300페이지 사양의 특정 측면을 준수하지 않았다는 보고서를 받고, 그 의미를 파악하기 위해 오랫동안 고민했다고 함
- 취약점 재현 단계는 버그헌팅을 모르는 사람이 봐도 따라할 수 있을 정도로 명확해야함
만약 Chrome 확장 프로그램에서 취약점을 발견했다면?
    1. OO Chrome 확장 프로그램을 설치한다.
    2. Chrome://extentions/페이지에서 확장 프로그램의 ID를 가져온다.
    3. -/.confing/google-chrome/Default/Extensions/{ID here}로 이동한다.
    4. 확장 코드가 포함된 OO javascript 파일을 찾는다.
    5. 확장프로그램의 백도어의 스크립트이다.
    [script]
    6. 확장 프로그램은 임의의 페이지를 악용할 수 있고, 예를 들어 Gmail 메시지를 추출해 타사 페이지에서 비밀번호를 획득할 수 있다.
- 코드 결함을 찾는 것만큼 성공적인 버그 헌터를 만드는 것은 복잡한 공격 시나리오에 대해 생각하고 명확하게 설명할 수 있는 능력
- 성공적인 공격 시나리오를 작성하기 위한 팁
    - 공격자의 시작 위치를 생각하라. 공격자가 이미 접근할 수 있는 것과 없는 것의 분류
    - 피해자에 대한 가정을 명확히 하라.
    - 공격에 대한 전제 조건과 파급력을 끌어올릴 방법을 생각하라.
    - 공격자와 피해자가 해야 할 일을 올바른 순서로 단계별로 기록하라.
    - 보고 전 항상 요약을 읽고 따라하기 쉬운지 확인하라.

## 마크다운 사용법

### 마크다운

- 웹에서 텍스트를 형식화하는 데 사용되는 경량 텍스트 기반 마크업 언어
- 순수한 텍스트 형식으로 작성되어, 가독성을 유지하면서도 웹에서 표현력있게 표현할 수 있게 하는 것이 주 목적
- 복잡한 HTML 태그 없이도 텍스트를 형식화할 수 있음. 이를 통해 제목, 하이퍼링크, 이미지, 목록 코드 블록 등 다양한 요소를 표현할 수 있음
- 버그 헌팅 보고서 작성에 필요한 간단하면서도 효과적인 포맷팅 언어
