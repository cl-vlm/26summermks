### IDOR 버그헌팅 사례 소개

“Stealing Your Private YouTube Videos, One Frame at a Time”

→ 5000달러 보상, 2019-12-11

상황 설정: 사용자B가 자신만의 이용을 위해 유튜브에 비공개 동영상을 업로드함

이 비공개 동영상은 기본적으로 사용자B 자신 또는 그가 직접 접근 권한을 부여한 사람들만 볼 수 있는 형태이다. 이는 유튜브에 기본적인 보안 메커니즘에 의해 보장되는 부분이다.

그런데 다른 사용자인 사용자A가 이 비공개 동영상의 URL 링크를 어떤 방법으로든 얻었다고 가정해보면 정상적인 상황에서는 이 URL을 가진 사용자A가 이 비공개 동영상을 접근하려고 해도 볼 수 없다.

그리고 알아야 하는 것은 Google Ads에서는 구글에 대해 광고 설정 화면에서 광고의 특정 요소(회사의 로고, 특정 상품의 이미지, 상품의 이름 등)를 광고에 추가할 수 있는 기능이 제공된다.

이러한 요소들을 추가하기 위해 제공되는 버튼의 이름을 MARK MOMENT라고 하는데 이 버튼을 누를 때마다 서버로 특정 HTTP 요청을 보내게 되는데 이 과정에서 발생하는 데이터 트래픽을 분석해 보면서 제보자는 취약점을 발견할 수 있게 된 것이다.

POST 요청의 본문인 바디 페이로드에서 동영상 고유 ID, Timestamp 이 두 값이 있다. 고유 ID는 유튜브의 동영상을 구별하기 위해 사용되는 고유한 값이다. Timestamp는 말그대로 동영상의 타임스탬프 값으로 밀리세컨드 단위로 측정된다.

POST 요청에서 GetThumbnails(겟썸네일)이라는 이름의 포스트 요청을 보내면 응답으로 동영상의 썸네일 이미지를 base64에 인코딩된 형태로 받게된다. 

즉, 하나의 요청을 통해 가져온 하나의 썸네일 이미지가 영상의 특정 시점을 가져올 수 있기 때문에 영상의 각 프레임을 하나하나씩 가져와 이를 모두 하나의 동영상으로 합침으로써 비공개 영상을 확인할 수 있다는 점에서 큰 가치를 가질 수 있게 되었다. 

### XSS 버그헌팅 사례 소개

그누보드 5.5.8.3

→ bbs.howey의 search.php라는 페이지에서 별도의 필터링 없이 one table이라는 이름의 변수에 값이 삽입된다. 그리고 이 one table 변수는 getpaging이라는 함수의 네 번째 인자값으로 들어가게 된다.

그리고 이 getpaging함수의 네 번째 파라미터인 url파라미터에 one table 변수에 들어갔던 값이 삽입된다. 이 getpaging 함수의 url 변수는 만약 현재 페이지를 나타내는 cur_page 변수의 값이 보다 큰 페이지라면 HTML 태그인 a태그에 그대로 삽입해 sti변수를 반환한다.

그리고 다시 getpaging 함수의 반환 값에서 my2pages라는 변수에 들어간다. 

만약 사용자가 search.skin.php라는 페이지 또는 해당 php페이지를 include하고 있는 페이지에 접근했다고 하면 이렇게 one table 파라미터에 대한 별도의 필터링이 존재하지 않아 공격자와 삽입한 악성 스크립트가 그대로 삽입되어 XSS(Reflected XSS)가 발생한다.

### SQL Injection 버그헌팅 사례 소개

RCE로 제보한 버그헌팅 사례

→ 먼저 제보자는 먼저 쿼리에 점 하나를 삽입하여 결과를 확인했다. 그 결과 제보자는 SQL 쿼리 오류 메시지를 받게되었다. 이 오류 메시지를 통해 제보자는 대장 시스템이 사용하고 있는 데이터베이스가 마이크로소프트 SQL임을 확인할 수 있었다. 

그리고 작은 따옴표를 삽입함으로써 SQL 쿼리가 변경되어 오류가 발생하였고, 쿼리 구문이 그대로 출력된 것을 확인했다. 

이 취약점을 파고든 과정을 살펴보면 먼저 사용자 이름에 해당하는 유저 네임 파라미터에 SQL injection 쿼리를 계속 넣었지만 SQL injection이 불가능했다고 한다. 아마 사용자 이름의 경우 개발자들이 방어로직을 추가했을 것으로 추측된다. 

그래서 사용자의 이름 대신 유저 에이전트(웹 브라우저가 서버에게 자기 자신을 소개하는 문자) 필드를 이용하기로 결정한다. 보통 이 필드가 SQL 인젝션 공격에 이용되지 않기 때문에 개발자들은 이 부분에 대해 방어로직을 강화할 수 있다. 하지만 이를 burp suite를 사용해 변조를 시도했고, 성공했다.

### SSRF 버그헌팅 사례 소개

SSRF Dropbox

→ 어떤 기능의 요청 패킷에서 파일 레퍼런스 파라미터 값을 제보자 자신의 서버로 변경해 호출했을 때 요청이 온 것을 확인했다. (SSRF 가능성 확인)

app.Hellosign.com이 어떤 클라우드 서비스를 사용하고 있는지, WhatIsMyIPAddress.com 서비스를 사용해 호스트 네임을 확인했더니 AWS 20초를 사용하고 있다는 것을 알았다. 또한 데이터를 가져오는 곳까지 발견했다.

이런 주요 정보들이 들어있는 서비스를 알아내며 여러 시도를 했다.

우선 제보자가 호스팅한 서버를 파일 레퍼런스 파라미터에 입력하고 보내게 되면, app.hello.com은 호스팅된 bughunterserver.io를 호출하게 된다. 다시 이 bughunterserver.io는 119.254.169.254에 latest의 metadata로 연결해 resource를 찾으라는 응답을 보내게된다. 그리고 이 응답을 받은 app.hello.com은 EC2 instance에 metadata resouce를 조회하고 사용자에게 반환한다. 

이렇게 우회하며 최종적으로 원하는 결과를 얻게 되었다.

## 자동화 도구 실습

### SQLMAP

- 자동화 sql injection 및 데이터베이스 탈취 도구
- 다양한 데이터베이스 지원 (MySQL Oracle, MSSQL, PostgreSQL 등)
- 탐지, 인젝션, 탈취까지 자동화 지원
- 옵션 설정 따라 파일 시스템, 운영체제 엑세스까지 가능

#### SQLMAP in 버그헌팅

- 서비스 부하를 줄이기 위해 delay 사용 가능
- 운영 서비스 안전을 위해 risk 단계 설정 가능
- 탐지 우회를 위해 tor 사용 가능
- http request dump 캡쳐 편의를 위해 r 옵션 사용 가능
- sqlmap 자동화 도구로 쿼리를 얻어낸 후에는 수동으로 쿼리를 변조하는 것이 안

### JWT Crack

- JWT (JSON Web Token)
    - JSON 구조의 콘텐츠를 Base64UrlSafe로 인코딩한 다음, 비밀 키 또는 공개/개인 키 쌍을 사용하여 서명
- 기본적으로 HS256 알고리즘을 많이 사용하지만 다른 알고리즘도 선택 가능
- HS256은 대칭키를 SHA256로 해시한 HMAC으로 원문을 서명했음을 의미
- 때문에 원문을 조작하려면 크랙이 필요
- JWT 크랙 도구에는 jwtrack, jwt_tool 등이 있음

### Hashcat

- hashcat
    - 해싱된 비밀번호의 원문을 얻어내기 위해 사용되는 해시 크래킹 도구
- hashcat의 공격 방식
    - 사전 공격: 사전에 존재하는 비밀번호
    - 콤비네이터 공격: 두 단어를 합친 비밀번호
    - 마스크 공격: 이전에 누출된 비밀번호 패턴을 이용한 생성 규칙으로 만든 비밀번호
    - 규칙 기반 공격: 단어를 수정, 잘라내기, 확장한 비밀번
